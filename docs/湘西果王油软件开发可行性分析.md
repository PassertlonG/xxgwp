## 可行性分析

> 这份分析只对我自己负责。它用来在每次动摇时提醒我：这件事能不能做、要付出什么代价、我能不能承受最坏的结果。

---

### 1.1 技术可行性

**结论：可行，但必须收窄第一阶段的交付范围。**

- **已有验证**：old 分支的 prototype 已经证明 `Springboot + JPA + PostgreSQL + Redis` 后端方案可以跑通核心链路；Taro 4.x 的跨端编译在技术上也走通了。
- **真正的硬骨头**：订单的并发控制、库存扣减的一致性、微信支付回调的幂等性。这三件事 AI 可以帮我搭骨架，但**最终的正确性必须由我亲自设计并验证，没有任何捷径**。
- **之前反复踩的坑**：同时维护微信小程序、、Web 两套前端。

---

### 1.2 时间可行性

**结论：可行，但节奏必须接受“蚂蚁搬家”的现实。**

我白天要上班，每天能稳定投入的时间只有 **1.5 ~ 2.5 小时**（晚上或周末）。在这个约束下：

- 一个中型模块（如用户认证、商品管理）的实际周期是 **1-2 周**。
- 整个系统达到第一个可交付版本（MVP），预计需要 **3-4 个周**。这意味着要提前做好常态化推进的准备。

**我必须接受这个节奏**。不能用“周末狂写两天”的幻想来欺骗自己，也不能因为进度慢就跳过流程。AI 代理的真正价值不是加速，而是**确保我每次坐下打开代码的那 2 个小时，能稳定产出、不出废品、不埋坑**。

---

### 1.3 资源可行性

- **人力**：只有我一个人，身兼产品、架构、前后端、测试。
- **AI 资源**：OpenCode + DeepSeek V4 Pro，定位是“初级工程师 + 代码审查员”，不是主程。
- **基础设施**：个人电脑 + Docker 环境。
- **资金**：DeepSeek API 费用极低（百万元 token 仅需 1-12 元），可忽略不计。

**结论：资源够用，瓶颈在我自己，不在工具。**
